Surgical instrument carrier robot

An autonomous line-following robot designed to carry and deliver surgical instruments as a university engineering demonstrator. I was the sole software developer within an eight-person team, responsible for the modular embedded controller, navigation, delivery logic and software-side subsystem testing.

ROLESole software engineer in an eight-person team
TECHNOLOGIESArduino Uno · C/C++ · IR and ultrasonic sensors · stepper/DC motor control
OUTCOMELine following and delivery demonstrated; accepted mass and budget limits met

01 / PROJECT BRIEF

Requirements and design constraints

The team developed a mobile robot to follow a marked route, detect designated delivery locations and actuate an instrument rack. The concept addressed hospital instrument transport, but the prototype was a university demonstrator, not a clinically validated medical device.

Scope clarification: I wrote the software and prepared subsystem test sketches. Other team members developed the mechanical design, CAD, physical construction and electrical wiring. The complete robot was a team achievement.

02 / CONTROL SYSTEM

Dual-layer finite-state control

The base control layer handles continuous line tracking and recovery. A higher-priority sequence responds to ultrasonic detection of delivery plates and temporarily overrides normal navigation.

01FollowLine

Three TCRT5000 IR sensors feed proportional left/right speed correction.

02LostLine

Directional memory guides recovery when the marked line is temporarily lost.

03ApproachDropoff

Front ultrasonic sensor rising-edge detection begins the approach sequence.

04DeliverPackage

Rear sensor rising-edge detection initiates stepper-driven rack movement.

The firmware also uses a post-delivery cooldown to reduce duplicate triggering. It checks for a newly detected plate rather than treating every sample within detection range as a new event.

03 / ENGINEERING DECISIONS

Why the controller was designed this way

01

Proportional control, not full PID

Proportional motor-speed correction provided a simpler controller to tune for the robot's route and intended speed. Integral and derivative terms were not introduced without a demonstrated need.

02

Polling rather than interrupts

Sequential sensor reads simplified debugging and integration. The project did not establish measured interrupt-latency or deterministic timing advantages.

03

Rising-edge ultrasonic events

Previous and current readings were compared to prevent a stationary plate from triggering repeated deliveries; the firmware also included a 2,000 ms cooldown.

04

Separate hardware interfaces

Motor control, sensor acquisition, finite-state control and configuration were split into modules, allowing individual tests without rewriting navigation logic.

05

Hardware-independent simulation

Simulation mode injected predefined sensor inputs and substituted Serial output for physical motor commands so state transitions could be exercised before full hardware integration.

06

Central configuration

Pin assignments and tuning parameters were stored centrally, including base motor speed, ultrasonic distance threshold, plate-event timeout and delivery cooldown.

05 / SOFTWARE

Modular firmware and delivery routine

The source project separates the main state machine, configuration, type definitions, sensor interfaces, motor controls and line-following logic. Dedicated test sketches cover the DC drive, IR sensor readings, ultrasonic distance sensing, stepper mechanism and combined integration.

Delivery routine excerpt from project documentation:

void PackageDelivery() {
    SetMotorSpeed(0, 0);
    digitalWrite(DirPin, HIGH);

    for (int i = 0; i < StepsPerRevolution; i++) {
        digitalWrite(StepPin, HIGH);
        delayMicroseconds(StepDelay);
        digitalWrite(StepPin, LOW);
        delayMicroseconds(StepDelay);
    }
}

The drive is stopped before actuating the delivery mechanism. The stepping loop is blocking: straightforward for the demonstration sequence, but it would need reconsideration for asynchronous control or more demanding safety requirements.

06 / VALIDATION

Build, testing and results

01

Subsystem bring-up

DC motors, line sensors, ultrasonic devices and the stepper subsystem were checked with separate test programs prior to full integration.

02

State-machine simulation

Hardware-independent sequences checked control transitions and emitted simulated motor/sensor activity through the Arduino Serial Monitor.

03

Integrated demonstration

The team demonstrated line following and package delivery during the university assessment. The assembled system was reported to fit the required envelope.

04

Mass and cost checks

At 2,041 g, the final robot was 41 g above the nominal 2,000 g target but 59 g under the +5% accepted maximum of 2,100 g. The reported £244 cost was £31 below the £275 budget.

Evidence boundary: Original project files record the physical demonstration, code organisation, test sketches, mass and cost. They do not establish quantified repeatability, navigation tracking error, electrical reliability or clinical sterility compliance. These are not claimed as validated outcomes.

07 / REFLECTION

Key lessons and improvements

This project demonstrated how the reliability of a multidisciplinary prototype depends on clear interfaces and incremental integration. The most useful lessons were modular control logic, early subsystem testing, event-driven sequence design and evaluating the final robot against the actual acceptance criteria.

Potential future improvements include quantitative tracking-error tests, repeated delivery trials, a non-blocking stepper controller and an investigation of whether full PID improves cornering. These are proposals, not completed validation.
