ESP32 battery energy storage supervisory controller

A physical ESP32 runs C++ supervisory logic against a simulated 10 kWh battery in Python. A serial hardware-in-the-loop test bench verifies power limiting, state transitions, temperature derating, communication watchdogs and controlled fault recovery.

PLANT10 kWh Python SOC and lumped thermal model
CONTROLLERPhysical ESP32 · C++ state machine · USB serial
VERIFICATIONAutomated HIL tests · CSV results · fault injection

01 / OBJECTIVE

Separate the simulated battery from real embedded decisions

The plant calculates simulated state of charge and battery temperature. Python sends these measurements and requested power over USB serial; the ESP32 independently limits the request and returns approved power, operating state and fault information. Python then applies only the approved power to the next simulation step.

Scope: The battery, sensors, heat generation and cooling are mathematical simulations. The ESP32 hardware executes the controller but does not switch electrical battery power or provide certified battery protection.

02 / DESIGN

Model, supervisory state machine and protocol

The battery uses energy integration with 95% assumed charge and discharge efficiency. A single thermal state tracks internally generated heat and heat transfer to ambient using Cth dT/dt = Q̇gen − UA(T − Tambient).

04Verify

Python checks decisions against reference rules and records results.

Example exchange: DATA,60,25,3,1 → RESULT,2.000000,DISCHARGING,NONE. The 3 kW request is clamped to the controller's 2 kW discharge limit.

03 / MEASURED TEST OUTPUTS

Power limiting and dynamic state transitions

In a 900-second simulated discharge, the physical ESP32 restricted a constant 3 kW request to 2 kW. The battery model integrated SOC from 60% to 54.737%; these values are simulated battery outputs controlled by actual serial firmware decisions.

In a separate 300-second scenario, the ESP32 switched between discharging, idle, charging and power-limited discharging. The recorded command responses form the operating-state timeline.

04 / THERMAL CONTROL

Derating responds to simulated cooling

With initial simulated battery temperature of 50°C and ambient temperature of 25°C, approved discharge power began at 1.00 kW. Over 900 simulated seconds, temperature fell to 48.99°C and ESP32-approved power rose to approximately 1.10 kW, consistent with the configured linear derating rule.

05 / VERIFICATION

Fault injection, numerical boundaries and regression tests

Python automatically supplied invalid sensor inputs, overtemperature measurements and missing communications. The ESP32 latched faults, rejected unsafe resets and resumed derated operation only after accepted recovery inputs.

01

Boundary overshoot diagnosed

A strict SOC threshold test uncovered floating-point overshoot. A numerical guard band was introduced in the firmware and reference implementation; all six tested ESP32 boundary cases then passed.

02

Fault latching checked

Overtemperature and impossible SOC readings caused zero-power fault responses that persisted after subsequent valid inputs.

03

Watchdog recovery exercised

A 3-second loss of valid serial messages triggered a fault. Fresh zero-power measurements and an explicit RESET command were required for recovery.

The scripted 100-request run completed in 0.928 seconds of wall-clock time including Python and serial overhead; this is not a guaranteed ESP32 execution time or worst-case response latency.

06 / REFLECTION

What the test bench establishes

The central result is a reproducible separation of plant modelling and embedded supervisory control. The same decision rules were implemented in Python and C++, then checked through a physical serial loop, simulated operating scenarios and deliberate fault injection.

Limitations: The 10 kWh battery and sensors are simulated; no cells, contactors or inverter are connected. Thermal properties are uncalibrated demonstration assumptions. The software watchdog and fault reset are not independent hardware safety mechanisms. These results do not establish industrial battery protection or compliance with safety standards.

Future development: Parameterised controller configuration, firmware timing instrumentation, expanded serial protocol edge-case tests and a representative low-voltage experimental test rig.
